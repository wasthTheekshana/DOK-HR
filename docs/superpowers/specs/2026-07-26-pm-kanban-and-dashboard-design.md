# PM Kanban Board & Dashboard Redesign — Design Spec

**Goal:** Follow up on the initial `project_manager` role rollout ([2026-07-24-project-manager-role-design.md](2026-07-24-project-manager-role-design.md)) with a Jira-style Kanban board for milestone tracking, configurable board stages, a PM-specific dashboard, and a small visibility fix so PM can see the invoice prices it already has permission to set.

**Context:** The existing Project Planning page (`client/src/pages/ProjectPlanning.tsx`) shows milestones as a flat list per site, with a hardcoded 3-value status (`not_started`/`in_progress`/`done`). The dashboard (`client/src/pages/Dashboard.tsx`) has no `project_manager` branch, so PM falls through to the generic admin view (staff table, sites list) which isn't useful for project oversight. Site creation and invoice-price entry already work for PM via the existing create/edit form and API — the only gap is that the **view/detail modal** hides the Invoice Price column from non-admin roles.

**Tech Stack:** Same as the base PM role work — PostgreSQL, Express + TypeScript, React 18 + TypeScript + Tailwind CSS, Lucide React icons. No new npm dependencies (drag-and-drop uses native HTML5 DnD events).

## 1. Data Model Changes

### 1.1 New table: `milestone_stages`

```sql
CREATE TABLE IF NOT EXISTS milestone_stages (
  id          INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name        VARCHAR(50) NOT NULL,
  sort_order  INTEGER NOT NULL DEFAULT 0,
  is_done     BOOLEAN NOT NULL DEFAULT false
);
```

One shared list of stages used as Kanban columns for every site's board (not per-site). Seeded once, on first migration, with the 3 values that exist today so behavior is unchanged until PM edits the list:

```sql
-- Guarded by "table is empty", not a unique constraint + ON CONFLICT — this migration
-- block runs on every server boot (same pattern as the rest of config.ts), and an
-- unguarded INSERT would duplicate the seed rows on every restart.
INSERT INTO milestone_stages (name, sort_order, is_done)
SELECT * FROM (VALUES
  ('To Do', 0, false),
  ('In Progress', 1, false),
  ('Done', 2, true)
) AS seed(name, sort_order, is_done)
WHERE NOT EXISTS (SELECT 1 FROM milestone_stages);
```

Invariant: exactly one stage has `is_done = true` at all times. Enforced at the application layer (not a DB constraint, to keep the migration simple) — `stageController` rejects unsetting the only done-stage without designating a replacement first, and rejects deleting a stage that has `is_done = true` unless another stage is promoted in the same request.

### 1.2 `project_milestones` — replace `status` with `stage_id`

```sql
ALTER TABLE project_milestones ADD COLUMN IF NOT EXISTS stage_id INTEGER REFERENCES milestone_stages(id);

-- config.ts migrations run on every server boot, so the backfill+drop must be
-- self-guarding: once `status` is dropped, a later boot referencing pm.status
-- would error. Wrap in a check so it only ever executes once.
DO $$
BEGIN
  IF EXISTS (
    SELECT 1 FROM information_schema.columns
    WHERE table_name = 'project_milestones' AND column_name = 'status'
  ) THEN
    UPDATE project_milestones pm
    SET stage_id = ms.id
    FROM milestone_stages ms
    WHERE pm.stage_id IS NULL
      AND ((pm.status = 'not_started' AND ms.name = 'To Do')
        OR (pm.status = 'in_progress' AND ms.name = 'In Progress')
        OR (pm.status = 'done' AND ms.name = 'Done'));

    ALTER TABLE project_milestones DROP CONSTRAINT IF EXISTS project_milestones_status_check;
    ALTER TABLE project_milestones DROP COLUMN status;
  END IF;
END $$;
```

Confirmed via grep that `project_milestones.status` is read/written only in `projectPlanningController.ts` — no other controller, test, or frontend file depends on it, so dropping it is safe.

### 1.3 Deletion guard for stages in use

`DELETE /api/milestone-stages/:id` returns `409` with a clear message if any `project_milestones` row still references that `stage_id` — same "block, don't cascade" pattern used elsewhere in this codebase (e.g. site deletion guards).

## 2. Backend API

### New files

**`server/src/controllers/stageController.ts`**
- `getStages` — `GET /api/milestone-stages` (PM only) — returns all stages ordered by `sort_order`.
- `createStage` — `POST /api/milestone-stages` — `{ name }`, appended at the end (`sort_order = max + 1`), `is_done = false`.
- `updateStage` — `PUT /api/milestone-stages/:id` — rename, reorder (`sort_order`), or set `is_done = true` (atomically unsets the previous done-stage in the same transaction via `withTransaction`).
- `deleteStage` — `DELETE /api/milestone-stages/:id` — blocked (409) if in use or if it's the current done-stage.

**`server/src/routes/stageRoutes.ts`** — all routes behind `authenticateToken, requireRole(['project_manager'])`, registered in `app.ts` as `app.use('/api/milestone-stages', stageRoutes)`.

### Modified files

- **`server/src/db/config.ts`** — add the migration blocks from §1.1/§1.2, following the existing `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` pattern already in this file.
- **`server/src/controllers/projectPlanningController.ts`**:
  - `getSitesPortfolio` — milestones query joins `milestone_stages`; `CURRENT_STAGE` becomes the stage `name` of the first non-done milestone (by `sort_order`, then stage `sort_order`); progress % = count of milestones whose stage `is_done = true` ÷ total; risk computed only for milestones whose stage `is_done = false`.
  - `getSitePlan` — milestones include `STAGE_ID`, `STAGE_NAME`, `IS_DONE` (joined), risk computed the same way.
  - `createMilestone`/`updateMilestone` — accept `stage_id` instead of `status` (defaults new milestones to the current lowest-`sort_order` stage, i.e. "To Do").
- **`server/src/utils/kpiUtils.ts`** — `computeMilestoneRisk` signature changes from `(dueDate, status, today)` to `(dueDate, isDone, today)`, checking `isDone === true` instead of `status === 'done'`. Existing Date-object handling from the earlier bugfix is unaffected.
- **`server/src/schemas/validationSchemas.ts`** — `createMilestoneSchema`/`updateMilestoneSchema` swap `status: z.enum(...)` for `stage_id: z.number().int().optional()`.

## 3. Frontend: Kanban Board

**`client/src/pages/ProjectPlanning.tsx`** site-detail view is reworked from a milestone list into a board:

- One column per `milestone_stage`, ordered by `sort_order`, header shows stage name + card count.
- Each card: milestone name, due date, risk badge (🔴/🟠), click to open the existing edit form (unchanged fields, just `stage_id` instead of a status dropdown).
- Drag-and-drop via native HTML5 events (`draggable`, `onDragStart` storing the milestone id, `onDragOver`/`onDrop` on each column calling `PUT /api/project-planning/milestones/:id` with the new `stage_id`). Optimistic UI update, rollback on request failure (toast error).
- A gear icon opens a **"Manage Stages"** modal: reorderable list (up/down buttons, no extra DnD library needed for this small list), rename inline, delete (disabled/tooltip-explained if in use or is the done-stage), a radio/checkbox to mark a stage as the done-stage, "Add Stage" button.
- The portfolio (site list) view is unchanged in layout; `CURRENT_STAGE` and progress % just now reflect PM-defined stage names instead of the fixed 3.

**`client/src/types/index.ts`** — add `MilestoneStage { ID, NAME, SORT_ORDER, IS_DONE }`; update `ProjectMilestone` to have `STAGE_ID, STAGE_NAME, IS_DONE` instead of `STATUS`.

`client/src/pages/Sites.tsx` — add `project_manager` to the `(role === 'admin' || role === 'system_admin')` condition around the Invoice Price column/header in the view modal (lines ~598, 605-607, 614-618), so `project_manager` sees the prices it's already permitted to set via the create/edit form. Pure display change, no API or permission change (the API already returns this data to PM).

## 5. Frontend: PM Dashboard

`client/src/pages/Dashboard.tsx` gets a new branch: `if (role === 'project_manager') { ... }`, placed alongside the existing `role === 'system_admin'` branch, using data from the existing `GET /api/project-planning/sites` endpoint (no new endpoint):

- Stat cards: Total Sites, At-Risk Sites (red or amber), Understaffed Sites.
- "Milestones needing attention" list — every red/amber milestone across all sites, sorted worst-first, showing milestone name, site name, due date, risk badge; clicking navigates to that site's Kanban board.
- Quick links: Project Planning, Staff KPI (existing PM-only pages).

## What This Does NOT Do

- Does not make stages per-site — one shared stage list drives every site's board.
- Does not add a company-wide KPI trend chart to the dashboard (deferred; only the project-health overview is in scope).
- Does not add an approval workflow for PM-created sites — admin already has full edit rights via the existing `PUT /api/sites/:id`, and pricing/task-type entry by PM requires no admin sign-off (confirmed decision).
- Does not add a new drag-and-drop npm dependency — implemented with native HTML5 DnD.
- Does not change who can create sites or set invoice prices at the API level — that access already exists; this pass only fixes a frontend display gate and adds the board/dashboard UI on top.
